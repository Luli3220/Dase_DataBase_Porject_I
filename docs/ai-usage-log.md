## 2. 前期讨论与数据库设计

项目开始时，我首先使用 ChatGPT 分析问卷系统的基本需求，并重点讨论了几个会影响数据库结构的问题：匿名填写是否仍需要登录、重复填写是否保留历史记录，以及问卷发布后如何修改题目而不影响已有答卷。

在数据库模型方面，我们比较了将历史版本直接嵌入问卷、将版本独立存储，以及进一步拆分题目和选项等方案。考虑到完整问卷的读取方式、历史版本的保留和答卷数量的持续增长，最终采用四集合模型：

- `users`：保存用户账号信息。
- `surveys`：保存问卷基本信息及版本指针。
- `survey_versions`：保存各版本的题目、选项和跳转规则。
- `submissions`：保存用户的每次提交及其答案。

在这一模型下，题目配置与对应版本一起保存，发布后保持稳定；用户提交则独立存储，并关联相应的问卷版本。

讨论过程中，我们还逐步明确了几项重要规则。例如，匿名填写仍然要求登录，但创建者无法查看匿名填写者的账号；重复填写保留每次提交记录，统计时可以只选择最新一次；条件跳转只允许前进，并由后端重新验证实际填写路径。

这些讨论帮助我们把最初较为宽泛的功能需求转化为具体的数据结构和业务约束，也成为后续 Coding Agent 开发的依据。

详细设计见[数据库设计文档](database-design.md)与[规则说明](rule-specification.md)。

## 4. 遇到的问题与修改

项目开发过程中，部分问题在设计讨论时就已经显现，另一些则是在代码检查和实际测试中发现的。

**版本管理与跨版本统计。** 在设计重复填写功能时，我们发现仅仅保存最新答卷无法满足历史分析需求，而按版本分别选择最新提交又可能产生错误的有效统计结果。最终选择保留全部提交记录，并规定 `latest_only` 先跨版本确定每位用户的最新提交，再筛选目标版本。这一规则随后落实到 MongoDB 聚合管道，并通过集成测试验证。

**发布与并发一致性。** 问卷发布、草稿编辑和用户提交可能同时发生。为保证状态一致，系统采用草稿修订号检查、MongoDB 事务，以及先冻结版本再更新发布指针的方式。Agent 还通过并发测试和发布中断故障注入，检查冲突处理和恢复逻辑。

**输入校验的边界问题。** 代码审查时发现，极大整数可能在数值判断过程中引发转换溢出，严格的日期类型校验也需要兼顾正常的 ISO8601 输入。Agent 调整了相关处理逻辑，并增加极大整数、非法数字和日期格式等测试用例。

**页面展示与匿名保护。** 早期页面直接显示选项内部 ID，后来改为根据问卷版本显示对应的选项标签。后续检查中，我又提出非匿名答卷应显示注册用户名。Agent 通过批量查询补充用户名，并确保匿名答卷及历史匿名记录不会返回用户身份信息。此次修改新增了 11 项测试。

开发环境中也出现过 Python 依赖不一致、MongoDB 后台进程无法持续连接等问题。最终使用 Python 3.11 独立虚拟环境和本机 MongoDB 单节点副本集完成运行与测试，相关过程保留在[测试报告](test-report.md)中。

## 6. 总结与后续工作

通过这次项目，我对 AI 辅助开发有了更加具体的认识。ChatGPT 在前期帮助我梳理需求、比较设计方案；Codex Coding Agent 则将这些要求转化为可运行的系统，并完成了大量测试和文档整理工作。

其中让我收获较多的是数据库设计中的一些细节：如何选择嵌入与引用的边界、如何保证历史版本可以正确解释、如何定义跨版本的有效提交，以及如何协调匿名保护与用户身份管理。这些问题需要结合具体业务反复讨论，最终才能形成清晰的实现规则。

后续如果需要增加题型、跳转条件或统计功能，可以继续在现有架构上扩展。同时，对于大规模数据性能、Docker 容器运行、多节点故障恢复和公网部署等方面，还有进一步验证和完善的空间。
