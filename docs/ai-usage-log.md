# AI 使用说明与证据索引

本项目使用 ChatGPT 与 Codex Coding Agent 辅助完成数据库课程设计。ChatGPT 主要用于前期需求分析、数据库方案比较及技术问题讨论；Codex Coding Agent 根据确定的开发要求，完成主要代码实现、自动化测试与技术文档。

在这一过程中，我主要负责分析课程要求、明确业务规则、参与数据库方案选择，并针对实现中发现的问题提出修改与验收要求。具体代码编写、环境配置和自动化测试主要由 Agent 执行。

为了便于核对 AI 的实际参与情况，本说明从**设计决策、Prompt 输入、代码产物、问题修正和测试证据**五个方面整理开发过程。正式报告侧重设计原理与结果分析，本文则提供相应的过程记录和 GitHub 证据入口。

## 2. AI 工具的使用与任务分工

### 2.1 前期需求分析与方案设计

项目初期，我首先使用 ChatGPT 阅读和讨论课程要求，重点分析了系统中的用户、问卷、题目及填写记录之间的关系。

讨论过程中，我们发现，一些看似简单的功能要求实际上存在需要明确的业务语义。例如，匿名填写是否允许系统内部记录用户身份、重复填写是否覆盖历史记录，以及问卷修改后如何处理旧版本答卷。这些问题会直接影响数据库结构，因而需要在正式实现前确定。

在数据模型方面，我们进一步比较了三种组织方式：将多个历史版本嵌入同一问卷文档、将问卷版本独立存储，以及将题目和选项拆分为更多集合。最终选择由 `users`、`surveys`、`survey_versions` 和 `submissions` 组成的四集合模型。

这一方案的主要考虑是：题目、选项和规则通常需要整体读取，适合嵌入单个版本文档；历史版本和填写记录可能持续增加，更适合独立管理。同时，通过冻结已发布版本，保证历史答卷能够依据原有题目和规则进行解释。

### 2.2 Coding Agent 的具体工作

确定总体方案后，我将设计约束和功能要求整理为分阶段 Prompt，交由 Codex Coding Agent 实施。

Agent 主要完成了 MongoDB Schema 与索引、BSON 数据模型、规则引擎、FastAPI 后端接口、身份认证、前端交互、统计服务，以及单元测试、数据库集成测试和浏览器测试。

实施过程中，Agent 使用 PowerShell、Python、pytest、真实 MongoDB、httpx 和 Playwright/Chromium 等工具执行程序、定位问题并验证修改，而不只是生成代码文本。

需要说明的是，事务处理、乐观并发控制、接口字段过滤等具体代码主要由 Agent 完成。我的参与重点在于提出和明确设计要求、比较实现方案，并检查最终行为是否符合预期，而不是将 Agent 的代码修改记录为个人手工编码。

## 3. 关键设计决策与个人参与

相较于具体的代码生成，我在项目中投入较多思考的是以下几个问题。

**数据库模型与历史版本。** 我们没有直接采用最简单的问卷文档结构，而是结合数据增长和版本保留需求，对嵌入与引用的边界进行了比较。最终将问卷基本信息与版本内容分离，由 `publishedVersion` 和 `draftVersion` 管理版本状态，避免后续编辑影响历史答卷。

**重复填写与统计口径。** 对于同一用户多次填写，我倾向于保留每次提交，而不是直接覆盖旧记录。在引入历史版本后，我们进一步明确了 `latest_only` 的含义：必须先在整份问卷的所有版本中确定每位用户的最新提交，再筛选目标版本。这一判断直接影响 MongoDB 聚合管道的执行顺序。

**匿名保护与身份管理。** 我们将匿名定义为“对问卷创建者隐藏填写者账号身份”，而不是系统完全不记录身份。系统内部保留 `respondentId` 用于区分用户，同时通过 `anonymousAtSubmission` 保存每次提交时的匿名设置，避免后续修改问卷配置而暴露历史填写者。

**条件跳转与提交校验。** 条件跳转采用结构化规则，而不是为不同问卷编写固定判断。我们还明确了一个重要约束：只有实际填写路径上的必答题才需要回答。后端必须重新计算合法路径，不能仅依据前端提交的答案判断有效性。

这些设计决定随后被整理为开发规格，并落实到数据库模型、规则引擎及对应测试中。具体数据结构和实现方式见[数据库设计文档](database-design.md)与[规则说明](rule-specification.md)。

## 5. 开发中发现的问题与修正

项目实施并非一次完成。通过代码审查、实际运行和页面检查，我们发现了一些影响正确性或使用体验的问题。

**运行环境与依赖问题。** 初期本机 conda `db` 环境的 Python 版本为 3.10.21，低于开发规格要求；部分依赖也未正确安装。Agent 随后使用 Python 3.11.5 创建独立虚拟环境，关闭系统包继承，并固定依赖版本。MongoDB 在自动化宿主中还曾出现后台进程无法持续连接的问题，因此改为使用本机常驻的单节点副本集，以支持真实数据库测试和事务操作。

**输入校验的边界问题。** 代码检查发现，严格日期模型可能拒绝正常的 ISO8601 时间字符串，而极大整数可能在数值判断时引发转换溢出。随后调整日期解析及数值检查顺序，并增加相应边界用例。这些属于代码审查中识别的风险，不能全部视为已经发生过的运行故障。

**答卷展示与隐私保护问题。** 早期页面直接显示内部选项 ID，影响阅读体验。Agent 根据答卷对应的历史版本，将选项 ID 映射为显示标签。后续检查中，我又发现非匿名答卷只显示内部用户 ID，于是提出使用注册用户名展示的修改要求，并强调不得因此暴露匿名填写者。

针对这一要求，Agent 在保留原有数据模型的基础上，为非匿名答卷增加 `respondentUsername` 响应字段，通过当前页批量查询获取用户名，同时维持历史匿名记录的身份隐藏规则。修改后新增 11 项测试，相关结果见[用户名修正验证记录](evidence/respondent-username/README.md)。

**版本发布与并发一致性。** 问卷发布涉及版本冻结和公开指针切换，提交答卷又可能与关闭问卷、发布新版本等操作同时发生。系统最终采用修订号检查、MongoDB 事务，以及“先冻结版本、再切换发布指针”的方式处理这些情况。测试通过并发请求和人为注入发布中断，检查冲突处理与恢复行为。

最后一项主要属于设计与实现中的一致性难点，并非已经确认发生过数据损坏。我们将方案设计中识别的风险与实际执行中出现的错误分别记录，以保持问题说明的准确性。

更完整的开发过程、环境错误及修复记录见[AI 使用日志](ai-usage-log.md)和[实际测试报告](test-report.md)。

## 7. 总结与适用范围

通过本项目，我逐渐认识到，AI 辅助开发的关键并不只是提高代码生成速度，更在于能否把需求转化为明确、可验证的设计约束。

对于数据库课程设计而言，问卷版本如何保存、匿名身份如何处理、重复填写如何统计，以及并发情况下如何维护一致性，都需要结合实际业务作出判断。AI 能够协助实现这些规则并构造测试，但不能代替对方案适用性、数据语义和潜在风险的分析。

本项目的实际工作方式是：通过讨论明确需求与设计选择，再将约束交给 Agent 实施，最后依据代码、运行结果及测试证据检查是否符合预期。对于发现的问题，继续提出具体修正要求，并保留相应的修改记录。

目前，项目已完成本机环境下的主要功能验证。Docker 容器运行、公网 HTTPS 部署、大规模容量测试、多节点故障转移及其他浏览器引擎兼容性仍未进行实际验证。这些内容属于后续扩展与完善的方向，不纳入第一阶段已完成的测试结论。
