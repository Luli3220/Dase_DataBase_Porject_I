## 1. 前期讨论与设计选择

收到变更需求后，我们首先回顾了第一阶段将题目嵌入问卷版本的设计。这种方式便于整体读取和冻结问卷，但题目缺少独立身份，难以在不同问卷之间复用、共享和追踪修改历史。

围绕这一问题，我们与 ChatGPT 比较了直接复制题目、引用最新内容，以及单独保存题目版本等方案。直接复制难以保留共同来源，引用最新内容又可能使旧问卷随题目修改而变化。最终选择保留原四集合，新增题目定义、题目版本和题库三个集合，让题目独立管理，每次修改形成新版本，而问卷保存实际选用的版本及完整内容。

讨论中还明确：题目的全局身份与问卷内的局部 ID 分别使用；恢复旧内容应当生成新版本，而不是覆盖历史；共享题目不代表可以修改原题或查看他人的回答。这些约定成为后续实现的依据，详细方案见[数据库演进说明](database-evolution.md)。

## 2. Codex 辅助实现

方案确定后，我将讨论结果整理为实施 Prompt，要求在第一阶段代码上增量修改，保留原有功能、数据和测试。Codex 据此扩展数据模型、后端接口和原有网页，新增题目管理、题库管理及跨问卷统计模块。

开发过程中，Codex 使用 pytest、真实 MongoDB 和 Playwright/Chromium 等工具验证功能，并继续运行第一阶段测试，检查问卷发布、条件跳转、匿名保护和原统计功能是否受到影响。技术文档随代码更新，第二阶段的测试和使用记录则单独整理。

## 3. 实现中的问题与后续修正

第一轮实现通过了 150 项测试，但后续检查仍发现了需要调整的地方。我据此进一步明确要求，由 Codex 修改实现并补充测试，主要包括以下三项。

**编辑器的保存一致性。** 原页面分别保存问卷基本信息和草稿内容，如果后一步失败，可能只保存一部分修改。重新检查流程后，我们要求将两部分放在同一事务中处理，并在冲突时保留页面输入，不继续预览或发布。Codex 增加了统一保存接口，以及失败回滚和并发保存测试。

**归档题目的分页。** 选题器最初取得分页结果后才过滤归档题目，可能导致页面不足一页，总数也与实际可选题目不一致。修改后由后端先过滤，再分页和计数；管理页仍可查看归档记录。

**统计数量的解释。** 使用关系中的引用记录数、统计涉及的问卷数和实际回答数含义不同。我们重新明确了无提交、跳题及旧答卷被新版本替代等情况，完善界面说明和测试。这一项保留原有统计算法，重点是让展示与实际口径一致。

具体修改与验证过程见[保存、分页与统计修复说明](fixes-2026-10-27.md)。

这一阶段的 AI 使用是持续的方案讨论、实现、检查与修改。人工通过需求分析和设计比较确定演进方向，再结合实际使用过程提出调整；AI 提供实现和验证支持。首轮测试通过后仍发现保存与分页问题，也让我认识到，测试能够验证已有用例，却不能替代对使用过程和设计合理性的检查。
